# TC-E2E-005: vLLM queue lifecycle debugging workflow

**Objective**: Validate the end-to-end debugging workflow for
per-engine request lifecycle using structured queue logs, from
request submission through queue events to log query by pod name
and trace ID.

**Preconditions**:
- OpenShift 4.16+ cluster with RHOAI 3.6 deployed
- Inference pool with multiple vLLM engine pods in namespace
  `inference-e2e-ns`
- LokiStack deployed and collection pipeline active
- GPU-equipped cluster (for KV cache scenarios -- weekly cadence)

**Test Steps**:
1. Identify two vLLM engine pods in the inference pool:
   ```bash
   oc get pods -n inference-e2e-ns -l app=vllm \
     -o jsonpath='{.items[*].metadata.name}'
   ```
2. Send an inference request with a traceparent header:
   ```bash
   trace_id=$(openssl rand -hex 16)
   traceparent="00-${trace_id}-$(openssl rand -hex 8)-01"
   curl -H "traceparent: $traceparent" \
     -d '{"model":"granite-3b-instruct","prompt":"Debug test","max_tokens":50}' \
     http://<inference-endpoint>/v1/completions
   ```
3. Wait 30 seconds for log ingestion.
4. Query Loki by `trace_id` to find which engine processed the
   request.
5. Extract the `k8s.pod.name` from the returned log entries.
6. Query Loki by `k8s.pod.name` to see all activity on that
   specific engine.
7. Verify queue lifecycle log entries are present: at minimum an
   enqueue event and a dequeue event for the request.
8. Verify each queue event log includes engine identity
   (`k8s.pod.name`) and `trace_id`.
9. Verify filtering by `k8s.pod.name` returns only logs from
   that specific engine pod -- no entries from other pods (AC 10).

**Expected Results**:
- Loki query by `trace_id` identifies the specific engine pod
  that processed the request
- Queue lifecycle logs include both enqueue and dequeue events
  with `trace_id` and `k8s.pod.name`
- Filtering by `k8s.pod.name` returns only that engine's logs
- The debugging workflow (trace_id -> pod -> queue events)
  enables per-engine request lifecycle investigation (Use Case 2)
