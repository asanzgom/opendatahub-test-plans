# TC-E2E-002: Cross-component trace correlation through inference path

**Objective**: Validate that a single traced inference request
produces correlated log entries across all components in the
request path (EPP -> vLLM) queryable by a shared `trace_id`.

**Preconditions**:
- OpenShift 4.16+ cluster with RHOAI 3.6 deployed
- LokiStack and Tempo deployed
- Inference pool with llm-d EPP and multiple vLLM engine pods in
  namespace `inference-e2e-ns`
- W3C traceparent propagation validated end-to-end
- Collection pipeline routing logs from `inference-e2e-ns` to Loki

**Test Steps**:
1. Send an inference request through the EPP endpoint with a W3C
   traceparent header:
   ```bash
   trace_id=$(openssl rand -hex 16)
   span_id=$(openssl rand -hex 8)
   traceparent="00-${trace_id}-${span_id}-01"
   curl -H "traceparent: $traceparent" \
     -H "Content-Type: application/json" \
     -d '{"model":"granite-3b-instruct","prompt":"Summarize AI","max_tokens":20}' \
     http://<epp-endpoint>/v1/completions
   ```
2. Wait 30 seconds for log ingestion.
3. Query Loki by `trace_id` value.
4. Verify log entries appear from both EPP and vLLM components.
5. Verify the EPP log entry contains routing decision fields
   (engine selected, selection reason).
6. Verify the vLLM log entry contains inference processing fields.
7. Confirm all entries carry the identical `trace_id` value.
8. In the OpenShift Console, click the `trace_id` in a log entry
   and verify navigation to the corresponding trace in Tempo.

**Expected Results**:
- Loki query by `trace_id` returns log entries from at least two
  components (EPP and vLLM)
- Every returned log entry contains the identical `trace_id` value
- EPP log entry includes `service.name` identifying it as the EPP
  component
- vLLM log entry includes `service.name` identifying it as the
  vLLM component
- Log-to-trace navigation in Console opens the Tempo trace view
  showing spans from both components
